# Робота з MiniCafe на різних комп’ютерах

GitHub зберігає код та історію змін. Це не автоматична синхронізація кожного
натискання клавіші та не синхронізація баз запущених програм.

## Перший запуск на іншому комп’ютері

1. Отримай доступ до репозиторію через свій GitHub-акаунт або запрошення власника.
   Підключений AI-інструмент також повинен мати дозвіл саме до цього репозиторію.
2. Встанови Git і склонуй репозиторій. Адресу візьми з GitHub → Code:

```sh
git clone <адреса-репозиторію>
cd <каталог-репозиторію>
```

3. Передай помічнику AGENTS.md і нову задачу. Він має прочитати START-HERE-UA.md.
4. Підготуй середовище за START-HERE-UA.md. Потрібні залежності не зберігаються в Git.
5. Для випуску APK передай оригінальний keystore і паролі окремим приватним каналом.
   Без ключа можна працювати над кодом, але не робити сумісне release-оновлення APK.

## Початок кожної окремої задачі

Спершу перевір локальні зміни. Якщо вони є — збережи їх комітом у відповідній гілці,
не перезаписуй. У чистому робочому каталозі:

```sh
git switch main
git pull --ff-only origin main
git switch -c task/коротка-назва
```

Кожен комп’ютер/помічник працює у власній гілці. Не редагуйте одночасно один
спільний каталог через OneDrive/мережевий диск. Окремі копії Git безпечніші.

## Завершення роботи й передавання змін

```sh
git status
git diff
git add <лише-потрібні-файли>
git diff --cached
git commit -m "Короткий опис зміни"
git push -u origin HEAD
```

На GitHub відкрий pull request у main. Перевір код і тести, об’єднай PR.
На іншому комп’ютері актуальні зміни з’являться після git pull, а не самі собою.

Якщо продовжуєш незавершену задачу на іншому ПК, відправ гілку через push,
потім на іншому ПК виконай git fetch origin і git switch <назва-гілки>.

## Паралельні зміни

Доцільно розділити задачі: один помічник змінює сервер, інший UI чи тести.
Якщо інший PR уже об’єднаний, у своїй гілці отримай його перед завершенням:

```sh
git fetch origin
git merge origin/main
```

Конфлікти розв’язуй зі збереженням потрібної поведінки обох задач і повторною
перевіркою. Не приймай усі файли «нашої» чи «їхньої» версії автоматично.
Не відправляй примусово main і не вмикай автоматичний pull поверх незбережених правок.

## Що не потрапляє до репозиторію

- Робоча база, замовлення, фото користувача та резервні копії даних.
- Keystore, паролі, приватні токени та локальні .env.
- SDK/JDK, node_modules, кеші, тимчасові збірки, старі архіви.

Готові APK/EXE можна додавати до GitHub Releases окремо від історії коду після
повної перевірки. Це не оновлює автоматично вже встановлені програми.
Сам репозиторій не запускає сервер MiniCafe і не надає доступ до кафе.

## Перевірки

GitHub Actions виконує початкову перевірку JS, форматування та Python-синтаксису.
Це не повна перевірка APK/EXE. Для релізу обов’язкові перевірки з START-HERE-UA.md,
включно з локальним work/scripts/checks.py та перевіркою готових артефактів.

## Налаштування власника на GitHub

Рекомендовано приватний репозиторій. Інших користувачів запрошувати з мінімально
потрібними правами. Для main увімкнути вимогу PR/перевірок і заборону force-push,
якщо ці можливості доступні на тарифі та для обраної видимості репозиторію.
Не роздавати пароль від власного акаунта або release-keystore всім учасникам.
